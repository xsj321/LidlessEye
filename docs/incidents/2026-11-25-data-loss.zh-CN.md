# 数据丢失根因：已知的、未知的、以及现在怎么抓

这份文件记录 2026-11-25 那次「一周数据消失」的**全部证据**和**结论边界**。它不是推测，也不是免责声明：能证明的写下来，不能证明的写明不能证明，并说明现在的代码靠什么在同类事件发生时给出可执行的线索。

## 事故现象

`default` 租户在 0.1.41 重启后，从 **62 469 批 / 9.77 小时** 掉到 **1 671 批 / 0.25 小时**：

- 磁盘上只剩 `hour=498783` 这一小时（每张表 5 个文件）；
- `frames` 表只剩 `hour=0`；
- `<tenant>/.trash` 里有 88 个文件、共 572 KB；
- 租户限额不变（`retention_ns=604800000000000` 即 7 天、`max_disk_bytes=4_000_000_000`）；
- pod 时钟正确（15:19 UTC），不是时间跳变导致的批量过期。

## 已被排除的假设

| 假设 | 怎么排除的 |
|---|---|
| retention 误删 | 在本地用事故前的数据副本（10 小时 / 258 文件）跑 `serve --retention=7d --max-disk=4GB --storage-mode=disk --flush-interval=10s` 105 秒，**258 个文件一个没少**。prune 只删索引里超过 7 天或超出磁盘上限的数据，两者都不成立。 |
| 磁盘写满触发的清理 | 事故前后 `max_disk_bytes` 未触发，且 `df` 有充足空间。 |
| 时钟跳变 | pod `date` 与宿主一致，没有跨天跳变。 |
| flush 覆盖写 | flush 只追加新文件；旧小时的文件名不会重用（`part-<ns>-<seq>`）。 |
| trunk 索引重建把文件当孤儿删掉 | 重建只**列出**它看到的文件，不删除任何东西。 |

## 尚未证明的（必须写清楚）

1. **是谁删了那些文件**，没有证据。容器运行时的存储回收、hostPath 被外部清理、节点磁盘压力都可能是来源，但事故已经过去，日志里没有留下进行删除的一方。
2. 为什么恰好剩下最后 0.25 小时，而不是更早或更晚的窗口，也没有解释。
3. `.trash` 里的 88 个文件说明**确有删除动作发生**并且走的是我们自己的删除路径（trash 是我们删文件的缓刑区）。这与「外部清理」矛盾，与「我们的 prune 走错分支」又矛盾——两次本地复现都无法重现。这是本事故唯一自相矛盾的地方，没有更多证据前不做结论。

## 现在的防线

`crates/lidlesseye-server/src/fsck.rs`（0.1.143 起，每小时一次，也可 `POST /api/v1/fsck` 立即跑）：

- 遍历每个租户的 `<data>/tenants/<t>/tenants/<t>/parquet/<table>/hour=<h>/`，统计文件数、字节数、小时数；
- 校验每个 `.parquet` 的首尾四字节是 `PAR1` 且长度 ≥ 12 —— 截断文件记入 `unreadable`；
- 小时目录里一个文件都没有记入 `empty_hours`；
- **与上一轮的文件集合比较，少了的就是 `vanished`**，按完整路径列出。

`vanished` 是关键：retention 走索引、删完文件集仍然自洽，所以「文件不见了」是索引永远解释不了的一类变化。事故当天如果跑过这个检查，日志里会是

```
WARN on-disk check found a problem tenant=default files=128 vanished=20000 unreadable=0 empty_hours=0
```

并且 `GET /api/v1/fsck` 会带着完整路径清单，能直接指认是哪一轮、哪一小时、哪些文件消失。

## 实测证据（0.1.143，`disk` 命名空间）

```
$ curl -X POST localhost:4790/api/v1/fsck
{"fsck":{"at_ns":1795726561249612419,"elapsed_ms":1,
 "tenants":[{"bytes":9010313,"empty_hours":[],"files":128,"hours":54,
             "unreadable":[],"vanished":[],"tenant":"default"},...]}}
```

放一个 16 字节的合法探针文件后再跑，`files` 129、`hours` 55、`unreadable` 空；删掉它再跑：

```
{"vanished":["tenants/default/tenants/default/parquet/frames/hour=999999/part-probe.parquet"], ...}
```

路径精确到文件，行为符合设计。

## 故障注入（0.1.143 实测）

| 注入 | 结果 |
|---|---|
| 在 `frames/hour=0` 放一个 16 字节、首四字节是 `XXXX` 的文件 | `files` 129、`unreadable:["tenants/default/tenants/default/parquet/frames/hour=0/part-corrupt.parquet"]`，`/api/v1/health` 仍 200 |
| 删掉上一步的文件 | 回到 `files` 128、`unreadable` 空 |
| 放合法探针（`PAR1xxxxxxxxPAR1`）→ 跑一次 → 删除 → 再跑 | `vanished` 精确列出该路径 |
